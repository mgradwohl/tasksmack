# AGENTS.md

Guidance for every AI agent working in this repo (Claude Code, Codex, Copilot, and others). This file is the
canonical copy of the shared agent rules: `CLAUDE.md` imports it, and `.github/copilot-instructions.md` points
here for workflow and merge rules. Change the shared rules here, not in those files.

Build/test/lint/architecture detail lives in [CONTRIBUTING.md](CONTRIBUTING.md),
[tasksmack.md](tasksmack.md) and [.github/copilot-instructions.md](.github/copilot-instructions.md). This file
condenses what an agent needs every session; read those for the rest.

## GitHub workflow (issues, PRs, reviews, CI)

- `gh` is authenticated against `mgradwohl/tasksmack`; use it directly for issues, PRs, reviews, and workflow runs.
- Follow [CONTRIBUTING.md](CONTRIBUTING.md)'s "Pull Request Process" and "Code Review Expectations" sections: small
  focused PRs, full PR template, `clang-tidy`/`clang-format`/`pre-commit` run before opening, and CI green before
  requesting merge.
- Use the existing templates rather than freehand text: `.github/pull_request_template.md` for PRs,
  `.github/ISSUE_TEMPLATE/bug_report.md` / `.github/ISSUE_TEMPLATE/feature_request.md` for issues.
- Merge authority (#2247): you may merge your own PR, or enable auto-merge on it, once CI is green and every
  review thread on it is resolved. Never merge with `--admin`, never force-push, and never close a PR or an
  issue without asking first. Any other shared or hard-to-reverse action (merging a PR you didn't open, deleting
  branches or tags you didn't create, editing releases) still needs the maintainer's go-ahead. Opening a draft
  PR, pushing a first version, and commenting/reviewing are fine to do directly when asked.
- CODEOWNERS auto-requests `@mgradwohl` on every PR — no need to manually assign reviewers.
- Never edit `CHANGELOG.md` — it's generated by `git-cliff` from a `v*.*.*` tag push and PR'd automatically.
- Treat `.github/workflows/*` edits as needing the maintainer's explicit confirmation before pushing, even though
  the `gh` token has `workflow` scope — CI/CD changes get extra human review on this project.

## Branches and backports (#2741)

Release branches from v0.9 on. Once the first one exists this replaces the freeze under "Release gating" below:
`main` is never frozen again, and `RELEASE_FREEZE` stays unset.

| Branch | What lands there | Milestones | Releases |
|---|---|---|---|
| `main` | all development: every PR targets it | the next minor (`v0.10.0`) | none directly: the maintainer cuts `release/0.10` from the approved candidate commit and tags `v0.10.0` there |
| `release/X.Y` | cherry-picks of fixes already merged to `main`, plus release mechanics only (version bumps, release-notes fixes) | that line's patch releases (`v0.9.1`, `v0.9.2`, ...) | `vX.Y.0` at the cut, then each `vX.Y.N` on the branch's head |

- **Upstream first:** every fix merges to `main` by the normal PR and is backported from there, so `main` is always
  a superset of every release branch. Never open a product-code PR against `release/*` directly.
- **The backport label:** put `backport:X.Y` (`backport:0.9`) on the `main` PR, before or after it merges. On the
  merge, `.github/workflows/backport.yml` opens the cherry-pick PR against `release/X.Y`, titled
  `<original title> [backport X.Y]`, with the original's labels and the open `vX.Y.*` milestone. For a label added
  after the merge, or a retry, comment `/backport` on the merged PR. A conflict fails that backport and the action's
  comment says how to cherry-pick by hand (`git cherry-pick -x <squash SHA>` onto `release/X.Y`, then a PR against
  it); the lane that owns the fix resolves it. A backport PR merges like any other: CI green, review threads resolved.
- **Which fixes:** an issue on a patch milestone (`v0.9.x`) gets the label on its `main` PR; a `v0.10.0` item doesn't.
  Security bumps get it like any fix. Renovate and Dependabot target `main` only.
- **Who cuts branches:** the maintainer creates `release/X.Y` from the approved candidate commit and pushes every
  tag; agents never create, delete or force-push a `release/*` branch. The "Main Builds" ruleset covers `release/*`
  with the same required checks as `main`, and CI, CodeQL, OSV, pre-commit, dependency review, ARM64, Sanitizers,
  Heavy Checks and main-health run on `release/*` pushes and pull requests too.
- **Changelog:** `changelog.yml` opens one `CHANGELOG.md` PR against the tag's release branch and one against `main`
  (the canonical, complete file); merge both. Never edit `CHANGELOG.md` by hand.
- **Branch life:** a release branch retires once the next minor ships, unless the maintainer keeps it for security
  fixes.

## Release gating (keeping later work out of a release)

**Only until `release/0.9` exists** (the maintainer cuts it right after v0.9.0, #2741); from then on "Branches and
backports" above applies and `main` is never frozen.

A release is tagged on the **exact candidate commit the maintainer approves** on the release tracker, not on main's
head. `release.yml` and `changelog.yml` only need the tagged commit to be on main's history, so anything merged after
the candidate is left out by construction. Two rules decide what may merge before then. Both lanes follow them for
every merge and every auto-merge they enable, including dependency PRs (Renovate, Dependabot).

- **Before the freeze** (the next release is planned but no candidate is approved yet):
  - **Merge freely:** PRs on the release's milestone, and any PR that changes no shipped code: docs, tests, agent
    guidance, test-only CI. "Shipped code" is `src/`, the build and packaging files under `cmake/` and the
    `CMakeLists.txt` files, and `release.yml`.
  - **Hold:** product code from a later milestone. Keep it open with auto-merge off until the release is tagged.
- **During the freeze** (from the maintainer approving a candidate until the tag is pushed): the maintainer sets the
  repository variable `RELEASE_FREEZE` to the release milestone (`gh variable set RELEASE_FREEZE --body v0.9.0`) and
  deletes it after tagging.
  - **Check first:** before merging a PR or enabling auto-merge, run `gh variable get RELEASE_FREEZE`.
  - **If it's set,** only PRs on that milestone merge. Turn auto-merge off on any other PR whose auto-merge is on,
    and don't approve Renovate dashboard updates.
  - **Validation finds a bug:** the fix goes on the release milestone and merges, and the maintainer approves a new
    candidate commit.
- **Who controls what:** agents never set, change or delete `RELEASE_FREEZE`, and never move an issue or PR onto
  the release milestone to get it past the freeze. Both are the maintainer's calls.

## Quick reference (condensed from CONTRIBUTING.md / copilot-instructions.md)

Architecture: `Platform` (raw OS counters only) → `Domain` (deltas/rates/history/immutable snapshots) →
`Core` (SDL3 window/loop, `PathService`) → `UI` (ImGui/ImPlot, never touches Platform) → `App` (panels; the
only composition root allowed to call `Platform::make*Probe()`/`Platform::makeProcessActions()`, only at
construction/`onAttach`, never in render loops; the panels' real-or-synthetic platform objects all come from
`App/PanelPlatforms.cpp`, wired by `App/ShellPanels`). OpenGL calls confined to `Core`/`UI`.

Sampling and drawing are separate (maintainer decision, #2731):
- **Settings interval:** every metric is sampled at the refresh interval the user chose in Settings, always. Nothing
  rescales it: not tab visibility, not interaction or resizing, not a minimized window, not the frame rate.
- **The UI thread:** only reads published, immutable snapshots, then formats and draws. It never calls a probe,
  makes a blocking syscall or does file I/O. Probes are built and seeded on their sampler thread, not in `onAttach`.
- **Separate cadences:** each data domain samples on its own worker, so one slow source can't delay another.
  Slow-changing facts run at a fixed constant from `src/Domain/SamplingConfig.h` (battery details, device
  rescans). Nothing counts frames to time work.

Feature parity: a metric with a system-wide tab should usually also get a Process Details tab for the
selected process and a Processes-table column (off by default unless common). And anything the Processes
table shows for a process should also be on its Process Details tab; one missing there is probably a bug.
See "Adding New Features" in [.github/copilot-instructions.md](.github/copilot-instructions.md).

Build (CMake Presets, `cmake --list-presets` for the full set):
```bash
cmake --workflow --preset dev        # Linux: configure+build+test
cmake --workflow --preset win-dev    # Windows equivalent
```
Common presets have a `win-` twin: `debug`, `release`, `release-compatible`, `optimized`, `relwithdebinfo`,
`coverage`, `unity`, `pgo-generate`/`pgo-use`/`pgo-baseline`, `profile`, `benchmark`. Linux-only: `asan-ubsan`, `tsan`, `msan`.

Format/lint (required before a PR is ready):
```bash
./tools/clang-format.sh              # or --changed-only for just the git diff
./tools/clang-tidy.sh debug
./tools/check-format.sh              # check without modifying
pre-commit run --all-files           # whitespace, UTF-8, REUSE, actionlint, guidance sync, ...
```

Test: `ctest --preset debug` / `ctest --preset win-debug` (Google Test; mocks in `tests/Mocks/MockProbes.h`;
use `EXPECT_DOUBLE_EQ`, not `EXPECT_EQ`, on floats).

Naming: `PascalCase` classes, `camelCase` functions, `m_PascalCase` members, `UPPER_SNAKE_CASE` constants.
Sampling literals live in `src/Domain/SamplingConfig.h` — reuse them, don't re-declare.

Python tooling (GLAD codegen, IWYU, pre-commit) expects the project venv: `source .venv/bin/activate` before
running `tools/*.sh` scripts that shell out to Python, if a venv exists at `.venv/`.

## Wayland-Native Support (PR #743, implementing #593; validation #865)

All platform-specific window behavior uses `Core::VideoBackend` abstraction:

**Backend Queries:**
- `VideoBackend::isWayland()`, `isX11()`, `isXWaylandFallback()`, `isWindows()`
- `supportsClientSideMaximize()`, `supportsGlobalMouseState()`, `usesSystemDrag()`, `usesSystemResize()`
- Never directly parse `SDL_GetCurrentVideoDriver()` outside VideoBackend

**Maximize/Restore:** Native Wayland delegates to the compositor. X11/XWayland ask the window manager to maximize
(`SDL_MaximizeWindow`) when it supports EWMH maximize (#1339), and otherwise position the window client-side.
Windows always maximizes client-side.

**Drag Handling:** The window's SDL hit test (`TitleBarLayer::hitTest()`, decided by `computeWindowHitTestAt()` in
`App/TitleBarGeometry.h` from the geometry the bar draws with) says who runs a title-bar drag and a border resize,
per `VideoBackend::usesSystemDrag()`/`usesSystemResize()`. Native Wayland hands both to the compositor
(`SDL_HITTEST_DRAGGABLE`, #744). Windows hands the empty title bar to its own move loop (`SDL_HITTEST_DRAGGABLE` ->
`HTCAPTION`), which is where Aero Snap, the snap preview and drag-to-the-top live (#2716), but keeps the border resize
client-side, since the OS resize loop would block SDL's event pump; a client-side maximized window's title bar stays
client-side too, so the drag restores it under the pointer (#2715). X11/XWayland keep the client-side drag and hand
the borders to the window manager. The client-side drag/resize reads window-local mouse state on native Wayland and
global mouse state elsewhere (`TitleBarLayer::queryMouseState()`). Buttons answer `SDL_HITTEST_NORMAL` everywhere.

**Compositor Safety:** Never assume GNOME/KDE/Sway/Hyprland specifics; implement graceful fallback. Test matrix: `docs/dev/wayland-test-matrix.md`.
